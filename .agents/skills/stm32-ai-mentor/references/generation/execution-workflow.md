# V2 固件执行工作流（受证据约束）

本流程服务于“帮我写好并烧录测试这个项目”的明确 V2 请求。主 agent 是唯一可写 `Projects/<project_id>/events.jsonl` 的角色；执行层仅返回 `ToolReceipt`，不得自行改变项目状态或学习掌握度。

## 进入条件

先冻结 `ProjectIntake`：`hardware_identity`（MCU、封装、开发板版本、板卡证据 SHA-256、由证据确认的 Flash 容量、丝印/照片/数据手册）、`execution_profile`（工具链、构建、探针、串口、允许动作）、`test_contract`（启动期限、串口帧、断言、超时/测量误差）和授权范围。板卡证据或 Flash 容量变化会改变 `target_signature` 并使旧执行证据失效。未知板卡、电压、负载、接线、探针或验收条件时，停止在信息收集或离线构建，不能给出确定接线或烧录。

运行输出统一写入 `Projects/<project_id>/runs/<run_id>/`：工具版本、命令收据、stdout/stderr、ELF/HEX/BIN/MAP、SHA-256、分析结果、串口捕获、失败分类和回滚基线。账本只写引用、哈希和结论。MCP 回复中的临时诊断正文不得直接塞进事件账本；只持久化符合 `tool-receipt.schema.json` 的收据及其哈希。

## 阶段门

1. **M0 环境与身份。** 检查固定工具链、工程目录、探针和串口。两个 ST-Link 或相同串口并存时，要求序列号/硬件证据选择，禁止“取第一个”。
2. **M1–M5 生成与离线验证。** 分增量生成、构建、分析 map、跑主机测试；模拟只能标为模拟证据，绝不升级为实机通过。
3. **M6 烧录预检。** 精确比对 `TargetIdentity`（探针序列号、MCU Device ID、只读工厂 Flash 容量、MCU 唯一 UID、板卡档案、目标电压）以及 baseline、地址范围和固件 SHA-256；展示风险与回滚点。调用方不能提交临时容量覆盖受管档案。板卡档案位于工作区外的哈希锁定策略中；只有照片/丝印复核后的 UID 与探针完成登记，档案才可从 inspection-only 升为可烧录。
4. **单次确认。** 每次 execute 都由 Codex 主机显示确认提示，并需要本轮明确同意的一次性令牌。目标、baseline、固件哈希任一变化立即使旧令牌失效。只允许把 BIN 的受管临时副本写入固定应用起始地址；ELF/HEX 只作检查与归档。禁止 raw shell、mass erase、Option Bytes、OTP/RDP/安全区和任意内存写。
5. **执行与验收。** write → verify → reset → 串口捕获 → 按 `test_contract` 判断。构建或 flash 成功不等于硬件功能通过。失败归类为构建、探针、供电、串口、I2C、传感器或显示，并回滚到最近通过的增量。

V1 可引用该实机证据作实践佐证，但不能把 AI 产出的结果自动记作学生独立掌握。V3 可复用收据，但仍独立核验规则、论文、创新和提交合规。

两个 MCP 服务的审查后副本安装在工作区外，并由启动器校验源码清单、外部权限策略、工具锁和二进制哈希。仓库内服务源码用于开发与测试，不能直接作为 Codex 自动启动入口。更新后运行 `scripts/install_execution_runtime.py` 完成显式替换并保留上一版运行时回退点。
