# 零硬件起步与采购决策工作流

本流程用于明确要“做出完整产品”、但用户手里没有开发板、模块、下载器或常用工具的 V2 请求。不要让小白先填写自己不可能知道的 MCU、封装、引脚或 MPN；先从使用场景、功能和验收结果推导候选硬件，再由用户做可理解的选择。

## 两阶段硬件身份

- **采购前候选护照**：记录需求、约束、2–3 个方案、推荐理由、候选 MPN/SKU、预算估算、替代件边界和到货核验项。它是计划，不是实物证据。
- **到货后实物护照**：用正反面照片、芯片丝印、包装标签、数据手册、实测电压、探针序列号和 MCU 只读身份把候选项升级为已核验实物。

采购前候选护照可以支持需求、方案、预算和离线固件准备；它不能支持确定接线、PCB 发布、烧录或 V5 实机结论。

## 新手默认阶段

1. **想法访谈**：每轮最多问 3 个真正改变方案的问题，优先询问使用环境、供电/负载、预算、尺寸、联网需求、精度和截止时间。未知技术项由导师研究，不反问用户“你想用哪款 MCU”。
2. **需求说明草案**：输出项目概述、功能需求、非功能需求、安全边界、量化验收标准、明确不做的内容和未决问题。先让用户选择“确认继续”或指出修改，不能把 AI 草案当作用户已确认需求。
3. **方案卡比较**：给出 2–3 个可落地方案，通常为“最低成本”“推荐均衡”“扩展升级”。每张卡写明最终体验、核心板卡/器件、预算区间、优点、缺点、学习难度、扩展性、风险和适用条件。标出一个 `Recommended`，并用生活化语言解释推荐依据；不要只罗列参数。
4. **用户选择**：允许用户直接选推荐项、改预算或提出偏好。`selected_option_id` 和 `selection_confirmation` 没有明确确认前保持 pending。
5. **完整采购清单**：从选中方案生成一次可审查的购物清单，不只列功能模块，还要覆盖：
   - 主控板与精确 MCU/板卡版本；
   - 传感器、显示、通信和执行器；
   - ST-Link、USB-UART、线缆、面包板/洞洞板、杜邦线和连接器；
   - 低压电源、限流/保护和电平转换；
   - 万用表等最低必需仪器；
   - 结构件/安装件、外壳、螺丝、焊接耗材和建议备件；
   - PCB 路线所需的封装、装配方式和分阶段采购项。
6. **逐项采购信息**：每项至少包含精确型号或可验证规格、数量、必需/推荐/选配、选择理由、供电与逻辑电平、接口、兼容性、参考价格区间、搜索关键词、允许替代件、禁止误买版本和到货检查方法。价格和库存是时效信息，实际采购前联网刷新并标注地区、币种、查询日期和来源；不能承诺库存或代替用户下单。
7. **采购确认门**：先展示总价范围、必买/可延期项、主要风险和仍未核实项。用户明确确认清单后才能冻结选中 BOM；确认不等于授权自动购买。
8. **到货登记**：用户按清单逐件标记 ordered/received，上传正反照片和标签。导师核对错版、克隆板、5 V/3.3 V 逻辑、缺少上拉/驱动/保护、接口方向和附件遗漏。
9. **实物基线**：只有到货核验后才创建 `hardware_identity`；目标板、器件或电源变化必须创建新 baseline，使不兼容的旧接线、构建和测试证据 stale。
10. **后续执行**：按开发板原型 → 离线构建 → 用户断电接线 → 单次确认烧录 → 串口/测量验收 → PCB 载板 → 自研主板推进。

## 默认采购策略

- 小白默认先买开发板和成品模块完成低压原型，再决定 PCB；不要一开始采购裸 MCU 全套制板物料。
- 清单分为 `必须购买`、`推荐购买`、`可延期`，并给出“现在买”和“原型通过后再买”两个批次。
- 所有选项必须满足当前验收条件；便宜但无法验收的方案不能作为有效选项。
- 不推荐来历不明的 MCU、无数据手册模块、只写“兼容”却不标逻辑电平的器件或无法确认版本的商品。
- 用户没有任何工具时，最低工具包通常包含万用表、可靠 USB 线、ST-Link、适配的杜邦线/面包板；具体清单随项目变化。

## 对话呈现契约

每次只要求用户做当前决策：先确认需求，再选方案，再确认购物清单。方案选项用可点击式编号或短表呈现，并把推荐项放第一。不要一次抛出完整数据手册、引脚表和几十个问题；技术证据可写入项目文件，聊天只解释选择会带来什么实际影响。
