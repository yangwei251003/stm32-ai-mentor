# V2 / V3 内部侧车契约

`stm32-ai-mentor` 是唯一公开入口。V1 项目课堂是默认核心；V2/V3 只有在明确意图命中后才加载，普通课堂不得主动展示或营销这两项能力。路由优先级为 V3 比赛、V2 完整项目、V1 学习。

## 状态隔离

- V1：`Student_Profile/`。V1 仅写 `learning.*`，其权威事件也仅为该命名空间。
- V2：`Projects/<project_id>/`，权威事件仅为 `generation.*`。
- V3：`Competitions/<competition_id>/`，权威事件仅为 `competition.*`。

三个账本通过稳定 ID 和不可变证据哈希引用，不做跨账本双写。`Student_Profile/state.json.extensions` 只能保存非权威侧车指针；缺失该字段不能导致项目或比赛状态丢失。V2/V3 证据需要影响掌握度时，主导师另写一条引用证据 ID 与哈希的 `learning.*` 事件。

## V2 工程边界：`stm32-project-builder`

V2 依次完成需求与量化验收、精确目标、安全与可行性、方案决策、BOM/供应、资源预算、接线、CubeMX、最小增量、构建/map、部署、测量/调试、验收、发布和复盘。任何关键未知都必须阻断依赖它的确定结论。

自动构建允许；每次烧录前必须展示目标、baseline、固件哈希和风险，并取得仅对本次有效的明确确认。生成烧录步骤或记录确认都不等于实际烧录，烧录成功也不等于功能验收。

## V3 竞赛边界：`stm32-competition-mentor`

V3 在选题、资格、截止时间、交付格式或合规判断前冻结当届官方规则。规则来源超过 7 天、发生更新或进入提交前检查时必须刷新；官方材料不可访问则降级为待核实准备建议。

V3 可以基于学生决策、原始数据、引用和贡献记录共创完整草稿，但不能伪造实验、图片、曲线、引用、创新性、获奖或回执。报名和提交始终由用户完成；只可用 `reported_by_user` 和回执证据记录结果。

## 共享事实纪律

构建成功只证明编译，烧录记录只证明部署，用户口述保持 `reported_by_user`。硬件功能必须有与目标签名和 baseline 绑定的实机证据。需求、目标芯片、封装或板卡变化创建新 baseline，并使依赖旧 baseline 的产物和证据失效，直至重新验证。
